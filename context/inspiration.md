## The pipeline, end to end

**Ingestion → extraction → graph → retrieval**, roughly:

1. Content arrives via `client.add()` (raw text, conversation turns, or an uploaded file/URL/connector sync), tagged with a `containerTag` (their equivalent of your branch — scopes memory to a user/org/project) and freeform `metadata`.
2. Their **Memory Engine** — an LLM-driven extraction step — pulls facts out, resolves them against existing memory (contradiction detection, supersession), and decides what's durable vs. noise. This is functionally identical in purpose to your `extract_units` + `_verify_unit`, just without a published two-pass architecture — from what's public, it looks like one integrated extraction/resolution step, not a separate verify pass like yours.
3. Extracted facts land in a structure they call the **Supermemory Graph** — entities, memories, and "contexts" as distinct node types. This is the closest thing to your entity-centric rework: they went further than a bare unit-graph and gave entities, memories, and *conversation-level context* three separate node types, all connected.
4. **User Profiles** are a derived, cached layer sitting on top of the graph — split into `static` (stable facts: "Senior engineer at Acme") and `dynamic` (recent activity: "debugging rate limits"), rebuilt continuously so a single `profile()` call returns both in ~50ms without a live search.
5. On query, **hybrid search** runs RAG (document chunks) and memory (graph facts) in the same call by default, merged into one ranked result set — this is their answer to "should retrieval treat facts and documents differently," and their answer is "no, blend them, let the caller filter by `searchMode` if they want one or the other."

## Storage

Two backends depending on deployment mode, both anchored on **Postgres**, not a dedicated graph database:

- **Hosted/enterprise**: Postgres + pgvector for vectors, running on Cloudflare Workers (edge-distributed compute) with R2/KV for object and session storage, Drizzle ORM for schema. No separate graph database (no Neo4j/FalkorDB) — the "graph" is a relational schema over Postgres, not a native graph engine. That's a real architectural choice worth noting given your own Zep comparison earlier: same critique applies here in reverse — they avoided Zep's "three systems minimum" problem the same way you did, by keeping the graph inside their primary store rather than bolting on a dedicated graph DB.
- **Self-hosted/local** (`supermemory-server`, the new one-binary local mode): everything lives under `./.supermemory`, embeddings default to a local `Xenova/bge-base-en-v1.5` (768-dim, same architecture family as your own `bge-base-en`) with zero API key required, and Postgres+pgvector is optional there too rather than mandatory — smaller local deployments can apparently run without standing up a full Postgres instance, though the exact embedded storage mechanism isn't detailed publicly.

## Detection, ranking, reasoning — architecture vs. prompt

This is the genuinely interesting part, and it maps closely onto something you already care about (evidence-first, don't trust vendor claims). Based on what's public:

- **Extraction and contradiction resolution are LLM-driven**, same as yours — "I just moved to SF supersedes I live in NYC" is explicitly named as the kind of judgment their engine makes, which is a semantic call, not a deterministic one. In self-hosted mode they say plainly: *you bring your own LLM for the intelligent steps — summaries, contextual chunking, memory extraction* — confirming this isn't proprietary architecture, it's prompting against whatever model you configure.
- **Embeddings are architecture, not prompt** — a real, separate vector step, locally computed by default, decoupled from the LLM entirely.
- **Ranking is hybrid** — vector similarity (pgvector cosine distance) blended with graph traversal signals, based on the "static/dynamic" profile split and the hybrid search default. Whether there's a learned reranker (cross-encoder, like yours) isn't disclosed publicly.
- **"Reasoned recall"** (mentioned in their Claude Code plugin) — the *decision* to search at all, each turn, before running any tool — is explicitly LLM judgment: "the agent silently decides whether recalling saved memory would improve its answer." That's the same shape as your `search_decision` classifier, just applied to memory search instead of web search.
- **Auto-forgetting** — temporal facts expire based on stated dates ("I have an exam tomorrow" → expires post-date). This sounds deterministic (a stored expiry timestamp) rather than LLM-judged at read time, which if true is a real advantage over a pure LLM-forget-detection approach like yours — cheaper and can't hallucinate a false forget trigger. Worth being skeptical though: this is their framing, not something independently verified.

**Honest read on "how much is architecture vs. prompt"**: probably closer to 60/40 prompt-to-architecture than their marketing implies. The genuinely architectural pieces are the graph schema, the vector store, the profile-caching layer, and the container/scope model. The actual *intelligence* — what counts as a fact, what contradicts what, when to forget, when to search — is LLM judgment wrapped in infrastructure, same as yours. Their real edge isn't "solved memory with pure architecture," it's operational maturity: caching, latency engineering, and benchmark-driven tuning done at a scale you haven't had reason to do yet.

## Latency and scalability — what's actually earning the speed

- **Edge compute** — Cloudflare Workers means requests execute geographically close to the caller, genuinely cutting network RTT versus a single-region backend (this is architecture-level, not prompt-related, and not something you can replicate in a self-hosted single-Rust-binary model without accepting the multi-region complexity that comes with it).
- **Profile caching** — the ~50ms number for `profile()` is almost certainly a cache hit against the continuously-rebuilt static/dynamic profile, not a live graph query — same principle as your pinned identity/preference units, just implemented as an actual cache tier instead of a retrieval-time sentinel score (and notably, their approach doesn't have your bug, because it's a genuinely separate fast path, not a hack riding inside the normal scoring pipeline).
- **Async ingestion, sync search** — explicitly documented: "searches are always served immediately... adds are accepted instantly but processed through a queue." Read/write are architecturally decoupled so a burst of writes never blocks a read — you don't have this distinction; your `commit_unit` is synchronous in the request path.
- **Local embeddings, prewarmed** — for the self-hosted binary, embedding workers are prewarmed at boot with a small worker pool, avoiding cold-start latency on first query.

## Fascinating things, genuinely

- **Container-tag identity resolution across coding agents** — Claude Code, Codex, and OpenCode share one memory container per repo, keyed by a hash of the *normalized git remote URL*, not the local path. Clone the same repo to two machines, same memory container automatically. Two differently-named repos with the same remote also collide correctly. That's a clever, deterministic identity scheme solving exactly the kind of cross-context entity resolution problem your entity graph solves for personal facts — applied to *repositories* instead of people.
- **SMFS (Supermemory Filesystem)** — treating memory as a filesystem an agent navigates with real commands, rather than a search API. Reported 3× fewer cumulative tokens on Claude, 1.75× on Codex, on a 110-question benchmark — while reportedly improving accuracy, not just cutting cost. If that holds up under independent testing, it's a genuinely different retrieval paradigm from either of your two current axes (semantic search vs. graph traversal) — closer to giving the agent `ls`/`cat`-style navigation over structured memory.
- **Reasoned recall as an explicit, named design principle** — deciding *whether to search at all* per turn is treated as a first-class UX/cost lever ("keeps more usage on your plan"), not just a latency optimization. You already do this with `search_decision`; seeing it named as a deliberate cost-control feature elsewhere validates the pattern.

## Weaknesses, real ones

- **Benchmarks are entirely self-reported and self-selected.** "#1 on LongMemEval, LoCoMo, and ConvoMem" — all three benchmarks, all numbers from their own paper, no independent replication cited anywhere in what's public. You already have the Zep/Mem0 LOCOMO dispute as a documented precedent for exactly this pattern in this space — treat these numbers the same way: plausible, unverifiable from outside, worth zero weight until someone with nothing to gain reproduces them.
- **True self-hosting is genuinely gated.** The GitHub README's local mode (`supermemory-server`, one binary) is real and free — but the *enterprise* self-hosting path (Cloudflare Workers + full Postgres deployment, matching their production architecture) is explicitly enterprise-only, contact-sales. There are two different "self-hosted"s being marketed under one word, and the free one is architecturally simpler than what actually powers their hosted product.
- **No dedicated graph database, but also no disclosed graph algorithm.** They call it a "graph," but it's schema-over-Postgres with no public detail on traversal — no PPR, no named algorithm, nothing comparable to Graphiti's documented approach. Could be genuinely simpler than it sounds, or the marketing term "graph" could be doing more work than the implementation.
- **"You bring your own LLM" self-hosted, but proprietary models in production** — their own docs state production uses "its own proprietary models tuned for long-horizon data understanding," while self-hosted users get whatever LLM they configure. That's a real, disclosed capability gap between the free/self-hosted tier and the actual product being benchmarked — the published SOTA numbers likely don't transfer to a self-hosted deployment running GPT-4o or a local model.
- **No auditability/versioning story anywhere in the public materials** — no git-style history, no "why was this forgotten," no branch/timeline concept. This is the one place your actual differentiator is untouched by anything here: contradiction resolution and auto-forgetting are described as happening silently and automatically, with no mention of a legible trail a user can inspect after the fact. That's the opposite instinct from Loki's whole trust posture.

## Bottom line for Loki

Nothing here is something you need to structurally copy — your entity-centric graph, git-versioned audit trail, and confirm-before-act pattern are still real, differentiated positions supermemory doesn't occupy. Three things worth actually stealing the *idea* of, not the code:

1. **Decouple read and write paths** — your `commit_unit` blocking the request is a real latency cost their async-ingestion model avoids. Worth considering for your own dispatch/action-layer design, not just memory writes.
2. **A genuine cache tier for pinned facts**, replacing your sentinel-score hack — same problem, cleaner solution, and it directly avoids the exact bug class we found and fixed a few sessions ago.
3. **Repo-identity-by-normalized-remote** is a small, elegant pattern worth borrowing if you ever build a coding-agent-facing memory container for Loki itself (relevant given you're actively using Claude Code to build Loki).
